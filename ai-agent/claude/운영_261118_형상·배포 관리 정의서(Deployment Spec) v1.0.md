## 1. 범위

- 소스 버전 관리(Git 저장소, 브랜치, 커밋, 이슈 연결)
- 변경 절차(이슈 → 구현 → 테스트 → 문서 → 승인 → 커밋 → 푸시)
- 환경 구분(개발 DB, 테스트 DB, 시연 계정)
- 빌드·테스트·실행 방법과 자동화 현황
- 데이터베이스 스키마 변경 관리
- 제외: 인터넷 공개 배포(기획서 D-3, 운영 정의서 9장 참고)

## 3. 브랜치 전략

- **현재**: `main` 에 직접 커밋한다. 혼자 작업하던 시기의 방식이다.
- **제안**: 팀 작업이 시작되면 다음 중 하나를 고른다.
  - (a) 기능 브랜치 방식: 이슈 번호로 `feature/이슈번호-짧은이름` 브랜치를 만들고, 테스트가 통과하면 `main` 에 병합한다.
  - (b) 현 방식 유지: `main` 직접 커밋. 대신 커밋 단위를 작게 하고 이슈와 연결한다.
- **권고**: (a). 한 사람이 실험하다 망가진 상태가 `main` 에 바로 올라가는 것을 막는다. 대표 결정 필요.

## 4. 커밋 규칙

1. **형식**: Conventional Commits. `타입: 설명 (#이슈번호)` (예: `feat: 즐겨찾기 서버 - favorites 표, … (#22)`)
2. **타입**: `feat` 기능 추가, `fix` 버그 수정, `docs` 문서, `refactor` 구조 개선, `test` 테스트, `chore` 기타, `style` 화면 모양
3. **크기**: 한 커밋에 한 가지 일만 담는다.
4. **이슈 연결**: 이슈 번호가 있으면 끝에 `(#번호)`를 붙인다. 현재 85개 중 48개가 이 규칙을 따른다. 나머지는 이슈 도입 전 커밋이다.
5. **승인**: 커밋과 푸시는 대표 승인 후에 한다. Claude 가 임의로 하지 않는다(CLAUDE.md Git 규칙 3번).
6. **커밋 전 확인**: `git ls-files -z` 로 추적 파일에서 비밀값(키, 비밀번호)을 검색한다.
7. **커밋 메시지 끝**: AI 작업 표기 줄을 붙인다(Co-Authored-By). 대표 지시에 따름.

## 5. 이슈 연결 (작업 추적)

| 항목 | 현재 |

| 도구 | GitHub 이슈 (`gh` 명령으로 조회·생성) |
| 제목 형식 | `[Type] 간결한 제목` (Type: Bug, Feature, Refactor) |
| 라벨 | 분석, 설계, 구현 + 기본 documentation, enhancement |
| 마일스톤 | `발표 2026-11-13` |
| 닫기 | 체크리스트를 확인한 뒤 대표 승인 후에 닫는다 |
| 번호 체계 | #1 산출물 8종, #2~#9 VS-0~VS-7 구현, #10~#13 발표 준비 문서, #14 단어 2,000개 확장 |

이슈 생성과 닫기는 외부에 보이는 동작이므로 대표 승인 후에 한다(CLAUDE.md 승인 목록).

## 6. 변경 절차 (한 사이클)

```
이슈 확인 → 현황 파악(코드·문서 직접 확인) → 설계 문서 갱신
→ 구현 → 자동 테스트 → 직접 확인(화면은 같은 동작 2회 이상)
→ 일지·문서 기록 → 대표 승인 → 커밋 → 푸시 → (승인 후) 이슈 닫기
```

- 한 사이클은 한 슬라이스(VS-0~VS-7 등)를 기준으로 한다.
- 자동 테스트가 실패하면 커밋하지 않는다.

## 7. 빌드·테스트·실행 (현재)

| 단계 | 명령 | 비고 |
|---|---|---|
| 백엔드 패키지 설치 | `cd src/backend` → `python -m venv .venv` → `.\.venv\Scripts\python.exe -m pip install -r requirements.txt` | 버전 고정 (`requirements.txt`) |
| 프론트엔드 패키지 설치 | `cd src/frontend` → `npm install` | `package-lock.json` 으로 버전 고정 |
| 자동 테스트 | `cd src/backend` → `.\.venv\Scripts\python.exe -m pytest -v` | 테스트 전용 DB(`smart_voca_test`)만 사용 |
| 화면 빌드 (확인용) | `cd src/frontend` → `npm run build` | 결과는 `dist/` (Git 제외) |
| 서버 실행 | `uvicorn app.main:app --host 127.0.0.1 --port 8000` | 자동 재시작 옵션 없음 |
| 화면 실행 | `npm run dev` (Vite, `localhost:5173`) | |

**자동화 현황**: CI(지속적 통합) 설정이 없다. `.github/workflows` 가 없어서 푸시할 때 테스트가 자동으로 돌지 않는다. 테스트는 사람이 직접 실행한다.

**제안**: 발표 이후 GitHub Actions 로 `pytest` 를 푸시마다 실행하는 설정을 추가한다. 발표 전에는 범위를 늘리지 않는다고 보고 보류한다(대표 결정 필요).

## 8. 환경 구분

| 환경 | DB 이름 | 용도 | 데이터 |
|---|---|---|---|
| 개발 | `smart_voca` | 실제 사용·시연 | 대표 계정, 데모 계정, 단어 2,000개 |
| 테스트 | `smart_voca_test` | 자동 테스트 | 테스트마다 전부 지우고 다시 만듦 |
| 복원 연습 | `smart_voca_test` | 백업 복원 확인 | 개발 DB 백업을 넣어 봄 |

- 설정은 환경 변수(`.env`)로 바꾼다. 같은 코드가 `.env` 값만 다르게 가진다.
- 테스트 DB 이름이 `smart_voca_test` 가 아니면 테스트가 스스로 멈춘다(개발 DB 보호).
- **제안**: 발표 이후 운영 환경을 만든다면 `.env` 를 환경마다 따로 두고 `JWT_SECRET` 을 새로 만든다(운영 정의서 9장).

## 9. 데이터베이스 스키마 변경 관리

1. 표를 바꾸면 Alembic 변경 파일을 만든다: `alembic revision --autogenerate -m "설명"`
2. **자동으로 만든 내용을 설계서(`Data Design`)와 대조해 확인한다.** 자동 생성은 빠뜨리거나 잘못 만들 수 있다.
3. `alembic upgrade head` 로 개발 DB 에 적용한다. 테스트는 매번 처음부터 다시 만들므로 변경 파일이 맞는지 자동으로 함께 확인된다.
4. 적용한 변경 파일 이름을 커밋 메시지나 일지에 남긴다. 현재 변경 파일은 8개다(`src/backend/migrations/versions/`).
5. 되돌리기: 개발 DB 에서는 `alembic downgrade` 를 쓰지 않는다. 되돌려야 하면 백업에서 복원한다(운영 정의서 6장). 테스트 코드는 `downgrade base` 로 테스트 DB 만 비운다.

## 11. 알려진 함정

- Windows 에서 `curl` 로 확인할 때 `/` 로 시작하는 문자열이 경로로 바뀔 수 있다(표시 문제).
- 서버 코드를 바꾸면 uvicorn 을 껐다 다시 켜야 한다.
- 화면 서버는 `localhost:5173` 으로 접속한다(`127.0.0.1` 은 연결 안 됨).
- `.env` 를 실수로 커밋하면 저장소 기록에 남는다. 이미 올라간 경우 값을 바꾸고 기록 정리를 따로 해야 한다. 예방이 최선이다.
