# 설계 결정 요약 (ADR)

**파일 위치**: `docs/설계_261118_설계 결정 요약(ADR) v1.0.md`
**작성일**: 2026-11-18
**버전**: v1.0 (초안, 대표 검토 전)
**설명**: 프로젝트 전체의 되돌아볼 만한 결정을 "무엇을 / 왜 / 다른 선택지는"으로 한 장에 모은다. 프로젝트의 주요 결정을 한눈에 보기 위한 요약이다. (이슈 #13)

> 원본 결정은 각 문서에 있다. 이 문서는 요약이며, 내용이 다르면 **원본 문서가 우선**한다. 원본 위치는 각 항목 끝 괄호에 적었다.
> 표기: 결정 번호는 원본 번호를 그대로 쓴다(D: 기획서, ADR: 기술 스택, AD: 아키텍처, DD: 데이터, IF: 인터페이스).

## 1. 기획 결정 (왜 이 서비스를 이렇게 만들었나)

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| D-1 | 대상은 **토익 학습자**로 한정 | 목표가 분명해야 단어와 기능을 집중할 수 있다 | 토플, 초중고생, 전체 |
| D-2 | 차별점은 **집중형**: 외운 경험을 끝까지 완성하는 것 | 간격 반복 + 시험 형식 연습 등 여러 기능을 섞으면 범위가 커진다 | 조합형(간격 반복 + 시험 형식 또는 AI 예문) |
| D-3 | 배포는 **로컬 실행**으로 한정 | 시연에 인터넷이 필요 없고, 서버 설정에 쓸 시간을 기능에 쓴다 | Docker 설정 포함, 클라우드 공개 배포 |
| D-4 | 기술 스택은 **FastAPI + PostgreSQL + React** (잠정) | 아래 2장 참고 | — |
| D-5 | 정답 확인(3단계 힌트)은 오답이 아니라 **"힌트 사용"으로 따로 기록** | 답을 본 것과 틀린 것은 다르다. 복습 점수도 다르게 준다 | 오답으로 처리 |
| D-6 | 범위를 **줄이지 않고** 기획의 기능을 전부 완성 | 기능이 빠진 것으로 보이지 않게 한다 | 필수/권장/선택으로 나눠 필수만 먼저 |
| D-7 | 구현은 **세로 방식**: 기능 하나를 화면·서버·DB까지 끝내고 다음으로 | 매 단계에서 실제로 동작하는 것을 보여줄 수 있고, 대표가 전체를 이해하며 진행할 수 있다 | 가로 방식: 화면 전체, 그다음 서버 전체, 그다음 DB |

## 2. 기술 결정 (무엇으로 만들었나) — ADR-001

- **결정**: 화면은 React, 서버는 FastAPI(파이썬), 데이터는 PostgreSQL.
- **왜**
  1. 대표가 자바스크립트를 접해 본 적이 있어 React 학습 부담을 감당할 수 있다고 판단.
  2. 화면과 서버를 API(주고받는 규격)로 나누면 구조가 명확해 설명하기 쉽다.
  3. PostgreSQL 은 대표가 SQL 을 배웠고, 실서비스에서 많이 쓰이는 무료 DB다.
- **다른 선택지**: (A) 서버에서 화면까지 만드는 방식(Jinja/HTMX), 가장 익숙하지만 화면 표현이 제한됨 / (C) Next.js + Supabase, 가장 빠르지만 내부 동작을 이해하기 어려워 "직접 이해" 목표와 충돌.
- **상태**: 잠정. 팀 회의에서 이견이 있으면 v1.1 로 갱신하기로 했다. **팀 회의 결과는 이 저장소에 기록이 없어 확인되지 않았다.** `[미확인]`

## 3. 구조 결정 (프로그램을 어떻게 나눴나) — 아키텍처 AD

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| AD-1 | 화면과 서버를 **분리**, JSON 으로 통신 | 역할이 명확하고 설명하기 쉽다 (ADR-001 재확인) | 서버가 화면까지 만듦 |
| AD-6 | 점수 계산(SM-2), 힌트 같은 **순수 계산은 `core_logic/` 폴더**로 분리 | 데이터베이스 없이도 빠르게 테스트할 수 있다. 계산 규칙을 바꿔도 다른 곳에 영향이 적다 | 서비스 안에 섞어 쓰기 |
| AD-8 | 결제를 **인터페이스 뒤에 숨김**: 토스 구현과 가짜 구현을 같은 모양으로 | 토스 연동이 막혀도 가짜 구현으로 바꿔 시연할 수 있다 (FR-SUB-08) | 서비스 코드에서 토스를 직접 호출 |
| AD-10 | 개발 중에는 화면 서버가 API 를 **대신 전달(프록시)** 해서 같은 주소로 보이게 함 | 같은 출처라 쿠키가 단순하게 동작하고, 다른 주소 간 허용 설정 실수를 피한다 | 서버에서 다른 주소 요청을 허용(CORS) |
| AD-11 | 설정(DB 주소, 비밀값)은 `.env` 파일에 두고 서버가 읽음 | 비밀값을 코드에 적지 않는다 (FR-SYS-03) | 코드에 직접 적기 |

## 4. 기술 세부 결정 — 아키텍처 AD

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| AD-4 | 데이터베이스 접근은 **동기 방식**(SQLAlchemy 2.1.6) | 코드 흐름이 단순해 설명하기 쉽다. 사용자 수가 적어 성능 차이가 의미 없다 | 비동기 방식, SQL 직접 작성 |
| AD-5 | 표 생성·변경은 **Alembic(마이그레이션)** 으로 관리 | 기능마다 표가 추가되므로 변경 이력이 필요하다 | `create_all` 한 번에 생성, SQL 파일 수동 관리 |
| AD-9 | 화면은 **JavaScript(JSX) + Vite + React Router + 일반 CSS** | 대표가 6일 안에 이해해야 해서 배울 것을 줄였다. 대가는 타입 검사 포기 | TypeScript, Redux, Tailwind |

## 5. 보안 결정 — 아키텍처 AD, 인터페이스 IF

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| AD-2 | 로그인 토큰을 **HttpOnly 쿠키**에 보관, 만료 **7일** | 화면 스크립트가 읽을 수 없어 훔치기 어렵다 | 브라우저 저장소(localStorage), 서버 세션 |
| AD-3 | 비밀번호는 **Argon2id** 로 해시 저장 | 원문을 저장하지 않는다. 검증된 라이브러리를 쓰고 직접 만들지 않는다 | bcrypt(대체 가능) |
| AD-7 | 퀴즈 문제에 **정답 영단어를 보내지 않음** (힌트 3단계 전까지) | 브라우저에 정답이 있으면 개발자 도구로 볼 수 있다. 정답 판정도 서버가 한다 | 정답을 보내고 화면에서 가림 |
| IF-5 | 힌트는 **같은 날 같은 결과** | 같은 힌트를 반복 요청해 정답 전체를 알아내는 것을 막는다 | 요청마다 새로 섞기 |

## 6. 데이터 결정 — 데이터 설계 DD (주요 항목만)

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| DD-1 | **학습 상태**(`user_words`)와 **학습 기록**(`review_logs`)을 두 표로 분리 | 상태는 지금 값이라 빨리 읽어야 하고, 기록은 이력이라 쌓기만 한다. 기록이 있어야 연속 학습일과 힌트 분석이 가능 | 기록만 두고 매번 계산, 상태만 두기 |
| DD-2 | 기록(`review_logs`)은 **추가만**, 수정·삭제 없음 | 기록은 사실의 이력이라 바뀌면 안 된다 | 수정 가능하게 |
| DD-3 | 숙련도(새/학습 중/익숙함)는 **저장하지 않고 계산** | 두 곳에 같은 정보를 두면 어긋날 수 있다. `[확인 필요]` 원문은 단어 500개 기준으로 쓰였고 지금은 2,000개다. 계산 비용이 여전히 작은지 다시 확인해야 한다 | 컬럼으로 저장 |
| DD-4 | **세션 표를 만들지 않음** (이어하기는 목록을 다시 계산) | 답할 때마다 상태가 바로 갱신되므로 다시 들어오면 이어할 수 있다. 표가 줄어 단순하다 | 세션 표로 진행 위치 저장 |
| DD-5 | 무료 범위는 **순위 250 이하**로 계산 (별도 컬럼 없음) | 요금제 범위를 바꿀 때 데이터를 고칠 필요가 없다 | `is_free` 컬럼 |
| DD-7 | 이용권 만료일은 **회원 행의 한 칸**(`premium_until`) | 지금 요구는 만료일 표시와 무료 복귀뿐이다. 이력은 결제 표가 이미 가진다 | 이용권 이력 표 |
| DD-8 | 날짜는 **한국 시간 기준 날짜**로 저장 | 사용자의 "하루"는 한국 자정 기준이다. UTC 로만 저장하면 날짜가 어긋난다 | UTC 시각만 저장 |
| DD-9 | 금액은 **정수(원)** | 소수 계산 오차를 피한다 | 소수 |

**DD-6 (결제 기록 보존)**: 결제 내역은 회원을 지워도 남기는 쪽으로 설계했다. 법적 보관 기간은 확인하지 않았다. `[미확인]`

## 7. 인터페이스 결정 — 인터페이스 정의 IF (주요 항목만)

| 번호 | 무엇을 | 왜 | 다른 선택지 |
|---|---|---|---|
| IF-1 | 모든 API 는 `/api` 아래 **JSON**, 이름은 `snake_case` | 서버와 DB 이름이 같아 변환이 필요 없다 | camelCase |
| IF-2 | **오류 모양을 통일**하고 코드 목록을 둠 | 화면이 코드로 일관되게 처리하고, 서버 내부 정보를 숨긴다 (FR-SYS-01) | 상황마다 제각각 |
| IF-3 | 가입하면 **바로 로그인** | 클릭 수를 줄인다 (NFR-USE-01). 가입 시 이메일 중복 여부가 드러나는 단점은 허용 | 로그인 화면으로 이동 |
| IF-4 | 한 단어는 **하루 한 번만** 복습 계산에 반영, 나머지는 연습 | 재시도를 허용하면서 점수 부풀리기를 막는다 | 제출마다 반영 |
| IF-6 | 결제 확인을 **다시 요청해도 같은 결과**(멱등) | 새로고침이나 중복 클릭에도 이용권이 두 번 늘지 않는다 (FR-SUB-06) | 두 번째는 오류 |
| IF-7 | 이용권이 끝나도 **배운 단어는 복습 가능**, 새 단어만 범위 제한 | 배운 것을 잃게 하면 경험과 신뢰가 나빠진다 | 만료 시 학습 전체 차단 |
| IF-8 | 오답 시 **정답을 알려주지 않음** | 재시도와 단계 힌트 설계를 지킨다. 정답은 3단계에서만 본다 | 오답 시 정답 공개 |

## 8. 자주 나오는 질문 (예시)

1. **왜 React 와 FastAPI 로 나눴나요?** → AD-1, ADR-001: 역할이 명확하고 API 로 주고받는 구조가 상용 서비스에 가깝다. 대가는 배울 것이 많다는 점이다.
2. **힌트 3단계를 왜 오답과 따로 기록하나요?** → D-5: 답을 본 것과 틀린 것은 다르다. 복습 점수도 다르게 준다(정답 5/4/3, 정답 확인 2, 오답 1).
3. **결제가 가짜인가요?** → AD-8, FR-SUB-08: 결제는 토스 테스트 키로 연동했고, 연동이 막혀도 같은 모양의 가짜 구현으로 바꿀 수 있게 나눴다. 실제 돈은 빠지지 않는다.
4. **정답이 브라우저에 가나요?** → AD-7: 힌트 3단계 전까지는 가지 않는다. 정답 판정도 서버가 한다.
5. **하루 목표를 넘으면 막나요?** → FR-STUDY-04: 막지 않는다. 목표는 안내용이고, 요금제 범위만 막는다.
